# ADR-0001: 将 GGFramework.Core 抽为独立仓库

- 状态：已接受
- 日期：2026-10-27
- 相关：ADR-0002；仓库 `GGFramework-Core`；`Singleton` / `CoroutineUtil` / `TaskSystem`

## 背景

GGFramework 各模块靠源码拷贝集成，共享基础类（`Singleton`/`CoroutineUtil`/`TaskSystem` 等）在每个仓库各存一份，已严重漂移（见 [vendoring-drift](../architecture/vendoring-drift.md)）。需要一个"单一源"消除漂移。

最初的落地方案是把 Core 包放在 **GGResource 仓库的 `packages/` 目录**（在 Unity 工程之外，不参与编译，作为"安全基础层"）。但复盘发现：Core 是**横切基础设施**，其内容来源本身就不中立——`Singleton` 的 canonical 版取自 GGUser、`TaskSystem` 取自 GGNetwork、`CoroutineUtil` 四仓一致。把它寄居在 GGResource 里存在几个问题。

## 决策

**将 GGFramework.Core 抽为独立 Git 仓库 `GGFramework-Core`，仓库根即 UPM 包根。**

## 理由与取舍

- **中立性**：Core 服务全部模块，不属于任何一个。独立仓库避免"某模块拥有公共基础"的错觉与所有权争议。
- **UPM 克隆成本**：UPM 即使使用 `?path=` 子目录引用，仍会 clone **整个宿主仓库**到 PackageCache。独立仓库使消费方只克隆 Core 本身，而非整个 GGResource。
- **独立生命周期**：Core 可单独打 tag、单独建 CI、单独设权限与版本节奏，不受宿主仓库牵制。
- **引用更简洁**：仓库根即包根，引用无需 `?path=`：`https://github.com/gonglei007/GGFramework-Core.git#v0.1.0`。
- **取舍**：多一个仓库需要维护（README/.gitignore/CI）；仓库数量从 5 增至 6（加 Docs 为 7）。相对中立性与克隆成本的收益，代价可接受。

## 被拒方案

- **留在 GGResource/packages/**：不中立、UPM 克隆整个 GGResource、无法独立打 tag/CI。
- **放进 GGFramework-Docs**：Docs 是文档仓库，混入可编译代码包语义不清。
- **新建 monorepo 合并全部模块**：与现有"每模块独立仓库"的组织方式冲突，迁移代价过大，且违背各模块可独立演进的现状。

## 影响

- 正面：Core 成为可被所有消费方 UPM 引用的单一源；迁移成本极低（迁移时 Core 尚未提交，几乎零成本）。
- Phase 1 范围：仅纳入**零第三方依赖**的 `Singleton`/`CoroutineUtil`/`TaskSystem`；`GameDebugger`/`ZipUtil`/`UIAdaptor`/`LogAdaptor` 因第三方耦合延后（见 ADR-0002）。
- 已验证：包在真实 Unity 6000.3.13f1 编辑器中编译通过，10 个 EditMode 用例全绿。
- 适用条件：在"Phase 1 不动命名空间、不删各仓副本、Core 不参与任何现有工程编译"前提下成立。接线消费方时进入 ADR-0002 的 Phase 2 约束。
