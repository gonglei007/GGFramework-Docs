# ADR-0003: Phase 3 改为副本对齐而非 Core.Optional 纳入

- 状态：已接受
- 日期：2026-10-29
- 相关：ADR-0002（接续其 Phase 3「待评估」的评估结论，不修改 ADR-0002 正文）；`GameDebugger`/`UIAdaptor`/`ZipUtil`/`LogAdaptor` 四类副本所在的 GGNetwork / GGUI / GGUser / Demo 仓库

## 背景

ADR-0002 的 Phase 3 原设想：把含第三方耦合的共享类（`GameDebugger`/`ZipUtil`/`UIAdaptor`/`LogAdaptor`）以 **Core.Optional 子程序集**纳入 `GGFramework-Core`，既单一源化、又不让 Core 主体背第三方依赖。

勘察后确认该设想**技术上大部分不可行**。`GGFramework-Core` 是 UPM 包（消费方经 PackageCache 引用），Unity 的编译顺序是**包先于工程**，因此 Core 的 asmdef **无法引用消费方工程 `Assets/` 下的第三方**：

- `CodeStage.AdvancedFPSCounter`：vendored 商业资产源码（`AFPSCounter.cs` 等），**无 asmdef**，落各工程 `Assembly-CSharp`；
- `ICSharpCode.SharpZipLib`：工程内预编译 `.dll`（`Assets/LocalPackages/UnityZip/`）；
- `SimpleJson`：单文件 `SimpleJson.cs`，**仅 GGUser 有 `SimpleJson.asmdef`**，其余仓库落 `Assembly-CSharp`，无稳定程序集可供 Core 引用。

即：Core.Optional 若要引用这些第三方，必须先把它们**都改造成可被 UPM 包引用的程序集**，成本与风险远超收益。

同时，四类副本的实况是：

| 类 | 副本 | 现状 |
|---|---|---|
| `GameDebugger` | GGNetwork / GGUI / Demo | 三版漂移；其中 Demo 是**有意禁用**（不自动加 FPS 计数器、不注册全局日志回调）的功能分叉版 |
| `UIAdaptor` | GGNetwork / GGUser | 除命名空间（各自专属）外，GGNetwork 版 `ShowDialog` 的 `else { callback(true); }` 有 **NRE 隐患**，GGUser 版已用 `callback != null` 修好 |
| `ZipUtil` | Demo / GGNetwork | 两版 MD5 相同，**已一致** |
| `LogAdaptor` | GGNetwork / GGUser | 除命名空间（各自专属）外**逐行一致** |

## 决策

Phase 3 **不把上述类纳入 Core**，改为**副本对齐（drift reconciliation）**——只消除无意义漂移与 P0 隐患，保留有意的行为分叉：

1. **`GameDebugger`**：以 GGNetwork 干净功能版为 **canonical**；GGUI 删除注释死代码对齐 canonical（功能不变，commit `e3af9ea`）；Demo **保留其有意禁用**并加中文标注（运行时行为不变，commit `df3c415`）。
2. **`UIAdaptor`**：把 GGUser 版的 `callback != null` **P0 修复回填**到 GGNetwork 版，消除 NRE 隐患（命名空间/签名不变，commit `407cfb0`）。
3. **`ZipUtil` / `LogAdaptor`**：核对确认已一致（`LogAdaptor` 的命名空间专属为有意设计——各模块有自己的适配器），**无动作**。

## 理由与取舍

- **尊重 UPM 硬约束**：包不能引用工程内第三方，是 Unity 编译顺序决定的，绕不过去；强行纳入需先把第三方全部 UPM 化，代价过大。
- **对齐即可消除主要危害**：漂移的核心危害是"源头修复不传播"与"无意义差异"。P0 回填 + 死代码对齐已消除这两点；`ZipUtil`/`LogAdaptor` 本就一致。
- **保留合理分叉**：Demo 的禁用是演示工程的**有意行为**而非漂移；`UIAdaptor`/`LogAdaptor` 的命名空间专属是各模块边界。强行统一反而改变运行时行为或破坏模块边界。
- **取舍**：副本仍然存在（未单一源化），未来仍需人工保持对齐；但相比"第三方 UPM 化 + Core.Optional"的巨大成本，这是当前性价比最高的处置。

## 被拒方案

- **第三方 UPM 化后再以 Core.Optional 纳入**：需把 AdvancedFPSCounter（商业资产、无 asmdef）、SharpZipLib（dll）、SimpleJson（多数工程无 asmdef）都改造成可被 UPM 包引用的程序集，成本高，且改动第三方源码/结构风险大。
- **接口抽象下沉（Core 定义接口、各工程注入实现）**：能解耦第三方，但要为 FPS 计数、Zip、JSON 各设计一套抽象并在每个工程注入，工作量与收益不匹配；且 `GameDebugger` 的价值恰在其具体实现。
- **强行让 Core.Optional 直接引用工程第三方**：违反 UPM 编译顺序，包编译期根本解析不到这些类型，不可行。

## 影响

- **正面**：消除 `UIAdaptor` 的 P0 NRE 隐患；`GameDebugger` 三版收敛为"canonical（GGNetwork/GGUI）+ Demo 有意分叉"两种明确形态；四类副本的无意义漂移清零。
- **负面 / 成本**：副本未单一源化，仍靠人工对齐；ADR-0002 设想的"这几类也走 Core.Optional 单一源"目标未达成。
- **后续**：命名空间收敛、GGResource/GGUI asmdef 边界、CI 等仍归 Phase 4（见 ADR-0002）。若将来第三方完成 UPM 化，可重新评估把这几类纳入 Core.Optional。
- **失效条件**：若 AdvancedFPSCounter / SharpZipLib / SimpleJson 未来都有了稳定可引用的程序集（UPM 化或补齐 asmdef），则"包无法引用工程第三方"的前提消失，本决策可被新 ADR 取代。
